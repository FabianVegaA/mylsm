# MyLSM 0.6.0.0 — API binaria, cursores y coordinación

**Fecha:** 2026-10-08
**Estado:** Borrador para revisión
**Release objetivo:** 0.6.0.0
**Alcance:** Una evolución integrada de la API durable, almacenamiento, lecturas, snapshots, coordinación entre procesos y herramientas de portabilidad.

## 1. Objetivo

MyLSM 0.6.0.0 debe convertir el motor en una base embedded LSM capaz de atender varias aplicaciones locales coordinadas, almacenar bytes arbitrarios y recorrer datasets grandes con memoria acotada. Las capacidades se publican como un contrato único: las APIs de texto y bytes comparten durabilidad, orden, snapshots, cursores y coordinación.

La versión busca una mejora sustancial de capacidad, no una secuencia de incrementos públicos incompletos. Internamente, la implementación puede organizarse en entregas verificables, pero 0.6.0.0 no se considera lista hasta que todas las capacidades incluidas satisfagan sus contratos y gates.

## 2. Decisiones de arquitectura

### 2.1 Un único propietario y varios clientes coordinados

Cada base tiene un solo proceso propietario canónico. Ese proceso posee el lock del sistema operativo, mantiene el estado LSM vigente y serializa todas las operaciones de escritura y lectura. Otros procesos se conectan como clientes mediante IPC local y nunca abren directamente los archivos activos ni mantienen una copia independiente del estado.

La interfaz de coordinación usa un socket local por base con permisos restringidos al usuario propietario. La ruta del socket se deriva de una identidad canónica de la base para que aliases de ruta no creen propietarios independientes. El protocolo incluye versión, límites de frame y validación de solicitudes. Los sistemas sin la primitiva local requerida fallan explícitamente; no se simula coordinación quitando el lock.

La cola de solicitudes tiene capacidad y límites de bytes configurados. Cuando se llena, el propietario aplica backpressure y devuelve un error tipado o deja que el cliente espere dentro de su timeout. El orden de aceptación es FIFO por conexión; entre conexiones se asigna orden al ingresar cada solicitud a la cola. El contrato no promete equidad temporal entre procesos.

El proceso propietario puede iniciarse explícitamente o mediante una apertura que tome ownership si aún no existe. La elección y ciclo de vida quedan visibles en la API: el primer proceso que adquiere el lock y publica el endpoint es propietario; los siguientes son clientes. El lock se mantiene mientras el propietario esté activo. Si este muere, el kernel libera el lock y un cliente puede iniciar recuperación y asumir ownership tras adquirirlo; ninguna solicitud de la generación anterior continúa ejecutándose.

### 2.2 Dos APIs públicas sobre un contrato de bytes

La API binaria acepta y devuelve claves y valores como secuencias de bytes de longitud explícita. No decodifica, normaliza ni convierte contenido a UTF-8. Distingue clave ausente de valor vacío y admite bytes cero, claves vacías y contenido UTF-8 inválido, sujeto a límites configurados.

La API UTF-8 expone claves y valores como texto. Valida entradas como UTF-8 y devuelve texto UTF-8. Si una lectura encuentra bytes que no forman UTF-8 válido, devuelve InvalidUtf8 sin alterar la base. En un cursor de texto, el elemento que causó el error no se entrega como Item; el cursor queda en estado Error y debe cerrarse. Es un adaptador de la API binaria, no un segundo formato ni un motor con orden independiente. No realiza normalización Unicode, conversión de mayúsculas, collation regional ni reemplazo de secuencias inválidas.

Los dos contratos son superficies públicas identificables y documentadas, con nombres que evitan confundir texto y bytes. La API binaria es la autoridad para persistencia y comparación; las operaciones de texto codifican sus argumentos a UTF-8 y decodifican sus resultados. Los límites se expresan en bytes en ambas APIs. Un error de decodificación nunca altera la base ni consume parcialmente un cursor.

### 2.3 Orden canónico

Todas las claves se ordenan lexicográficamente por byte sin signo. En el primer byte distinto, gana el menor; si una clave es prefijo de otra, la clave más corta va primero. Claves idénticas son la misma clave lógica.

Este orden se aplica sin variaciones a MemTable, SSTables, Bloom filters, límites y resultados de scans, merge, compactación, recuperación, snapshots, backups y coordinación. Los filtros Bloom usan la secuencia exacta de bytes. La API UTF-8 hereda este orden sobre la codificación UTF-8, que no se presenta como orden lingüístico.

### 2.4 SSTables por bloques y cursores

Los lectores de SSTable mantienen descriptores, metadatos e índices paginables; cargan bloques a demanda y verifican su checksum antes de exponer registros. Recuperación puede recorrer el contenido secuencialmente para verificar integridad, pero no retiene la tabla completa. Los índices y filtros también tienen límites y política de carga explícitos para que metadatos grandes no invaliden el presupuesto.

Un cursor ascendente acepta límites inferior y superior opcionales, con intervalo [inferior, superior), además de una opción de prefijo. El prefijo se interpreta sobre bytes y su intervalo equivalente se calcula en el orden canónico. Si no existe un límite superior representable para el prefijo, el cursor termina por comparación directa de prefijo.

El cursor ofrece posicionamiento inicial, lectura incremental, resultado Item/End/Error y cierre explícito. El posicionamiento permite buscar la primera clave mayor o igual que el límite inferior sin recorrer desde el inicio de cada SSTable. Cada clave lógica aparece una vez: gana el valor visible más reciente y se omiten tombstones. Cierre anticipado, End, cancelación y error liberan buffers y referencias. No se ofrecen tokens persistentes entre reinicios.

El coste de memoria del cursor es proporcional a fuentes activas, buffers configurados, metadatos paginados y el mayor registro admitido; no al número total de resultados. El límite máximo de registro forma parte del presupuesto y no se considera memoria gratuita. Los límites excedidos producen ResourceLimit antes de entregar un cursor utilizable o un resultado parcial declarado exitoso.

### 2.5 Snapshots y concurrencia de lecturas

Cada cursor queda asociado a un snapshot estable, explícito o creado automáticamente al abrir el cursor. El snapshot fija el estado lógico tras un batch completo y retiene raíces inmutables de memtables junto con la versión del conjunto de SSTables. `get` también puede ejecutarse contra un snapshot explícito.

Las solicitudes se serializan en el propietario, pero un cursor abierto no bloquea el procesamiento de nuevas escrituras. Flush y compactación publican nuevas versiones; los archivos viejos permanecen hasta cerrar el último snapshot o cursor que los referencia. El motor no requiere historial MVCC por registro.

La cantidad de snapshots, cursores, bytes de estructuras retenidas, bytes de SSTables retenidos y buffers tiene límites configurables y observables. Una operación que excedería el presupuesto falla con ResourceLimit sin invalidar snapshots existentes. Cerrar un snapshot con cursores activos y cerrar la base con recursos hijos activos devuelve Busy. Los snapshots no sobreviven reinicios.

### 2.6 Lock con espera y timeout

La apertura como propietario admite política de adquisición inmediata o espera con timeout explícito. La espera nunca roba locks por PID o antigüedad. El timeout devuelve Busy con información tipada de que expiró la espera. Una apertura como cliente se conecta al endpoint publicado y tiene su propio timeout de conexión.

El archivo de lock es estable y no se elimina ni reemplaza durante operación normal. El kernel libera ownership al morir el proceso. Se evita heredar el lock accidentalmente a procesos hijos. La implementación valida comportamiento en los sistemas operativos soportados. Si una plataforma no ofrece la garantía necesaria, devuelve UnsupportedPlatform.

### 2.7 Backup, restore e inspección de formatos

El backup lógico exporta una vista consistente usando un snapshot y cursores acotados. El archivo de intercambio tiene versión propia, orden canónico, longitudes explícitas, conteos, checksums por bloque y marcador final verificable. Preserva claves y valores byte por byte; no exporta WAL, historial de versiones ni snapshots activos.

La creación del backup usa temporal en el destino, sincroniza datos, publica con rename atómico y sincroniza el directorio. Rechaza destinos existentes. Una interrupción antes de publicar no deja un backup con nombre final.

Restore valida versión, límites, checksums, orden, duplicados y marcador final antes de publicar. Construye la base en un directorio temporal hermano del destino, sincroniza y reabre para verificarla; después publica atómicamente. No reemplaza destinos existentes. Ante error conserva intactos el origen y el destino preexistente.

La inspección offline informa versión de formato e integridad bajo lock, sin reparar ni descartar información. Las versiones de API, formato de base y formato de backup se versionan por separado. Versiones desconocidas se rechazan antes de modificar datos.

### 2.8 Migración desde la versión anterior

La migración soportada es desde bases durables abiertas por la API pública 0.5.0.0, incluyendo el formato de almacenamiento identificado actualmente como 0.4.0.0. La herramienta detecta y reporta ambas identidades para evitar confundir versión de paquete con versión de formato.

La migración lee la base fuente con un lector compatible, obtiene una vista consistente bajo ownership exclusivo, y escribe una base nueva en formato 0.6.0.0. No modifica la fuente. Verifica recuento, claves, valores y checksums antes de declarar éxito; la comparación lógica usa la codificación UTF-8 existente y el orden binario canónico. Corrupción, formato desconocido, falta de espacio o interrupción no publican una base final parcial. No se garantiza migración in-place ni soporte de formatos anteriores al origen documentado.

## 3. Operaciones y errores públicos

Las firmas definitivas se fijan en el diseño de API, conservando estas operaciones conceptuales en ambas superficies donde aplique:

| Operación | Contrato |
| --- | --- |
| `create` / `open` | Adquiere ownership o se conecta al propietario; permite timeout de lock/conexión. |
| `get` | Lee el valor visible actual o de un snapshot; distingue ausencia de valor vacío. |
| `put` / `delete` / `write_batch` | Serializa y confirma mutaciones; un batch es atómico y durable. |
| `scan` | Crea cursor por rango o prefijo asociado a snapshot. |
| `cursor_seek` / `cursor_next` / `cursor_close` | Posiciona, lee un resultado incremental y libera recursos. |
| `snapshot` / `snapshot_close` | Fija o libera una vista estable. |
| `flush` / `compact` | Publica nuevas versiones sin invalidar lectores existentes. |
| `backup` / `restore` / `inspect` / `migrate` | Exporta, verifica, inspecciona o transforma datos con publicación segura. |
| `stats` / `close` | Expone presupuestos y estado; cierra recursos respetando ownership. |

Los errores tipados cubren NotFound, AlreadyExists, Busy, Timeout, InvalidArgument, InvalidUtf8, UnsupportedFormat, UnsupportedPlatform, Corruption, ResourceLimit, ProtocolError, Io y CommitUnknown. Los errores mantienen operación y causa del host sin obligar al consumidor a interpretar texto libre.

Las solicitudes de escritura se asignan a una generación del propietario. El cliente recibe un identificador de solicitud para distinguir respuestas correlacionadas, pero el protocolo no promete exactly-once. Si se pierde la conexión tras comenzar un commit y antes de recibir respuesta, el resultado es CommitUnknown; el cliente no reintenta automáticamente. La recuperación posterior garantiza que cada batch confirmado antes de la respuesta se conserva entero o no se aplica; el resultado de una solicitud cuyo estado no se confirmó queda sujeto a CommitUnknown.

## 4. Límites y observabilidad

Las opciones públicas definen límites para tamaño de clave/valor y registro, bytes por batch, cola de solicitudes, conexiones, cursores, snapshots, bloques, índices residentes y bytes retenidos. Los valores predeterminados son finitos y documentados. Las opciones inválidas se rechazan antes de iniciar el propietario o modificar archivos.

Las métricas distinguen bytes activos, bytes retenidos por lectores, WAL, payload de memtables, buffers e índices residentes, cola y bytes en espera, conexiones, cursores, snapshots, bloqueos y errores. Se especifican unidades y si cada valor es persistente o de proceso. Payload no se presenta como RSS. La consulta de métricas no recorre todas las SSTables ni modifica datos.

## 5. Fuera de alcance

- Transacciones generales de lectura-modificación-escritura y aislamiento serializable.
- Ejecución física paralela de escrituras.
- Propietarios distribuidos, replicación, clientes remotos y filesystems de red.
- Exactly-once o reintentos transparentes tras CommitUnknown.
- Bindings de lenguajes y distribución de binarios como parte de este release.
- SQL, índices secundarios automáticos, búsqueda textual/vectorial o semántica de documentos.
- Migración in-place o compatibilidad con formatos anteriores al origen especificado.

## 6. Secuencia interna para un release integrado

La implementación puede avanzar por gates internos sin publicar contratos incompletos:

1. Fijar el formato 0.6, orden binario y límites; crear fixtures de compatibilidad 0.5.
2. Convertir memtables, filtros, codecs, recuperación, compactación y exportación a bytes y comparación canónica; conservar la API UTF-8 como adaptador.
3. Implementar lectura por bloques, índices paginables y recuperación sin materialización completa.
4. Implementar snapshots retenidos y cursores estables de rango/prefijo con presupuestos efectivos.
5. Implementar lock con espera, propietario canónico, endpoint IPC, cola acotada y clientes coordinados.
6. Implementar backup, restore, inspección y migración segura desde 0.5.0.0.
7. Integrar API pública, documentación, operación, recuperación y gates de rendimiento del release.

Estas etapas son dependencias de construcción, no versiones públicas. La coordinación multi-proceso se apoya en una API binaria y una única máquina de estado; cursor/snapshot se apoyan en lecturas por bloques; backup y migración consumen los contratos de cursor, snapshot y bytes.

## 7. Validación y aceptación

La aceptación de 0.6.0.0 requiere evidencias independientes para leyes puras, fixtures concretas y comportamiento del host. Las pruebas de crash/IO y las comprobaciones de locks se reportan como evidencia empírica del host, no como teoremas formales.

| Área | Evidencia requerida |
| --- | --- |
| API bytes y UTF-8 | Round trip binario incluyendo cero, secuencia inválida UTF-8, bytes vacíos, valor vacío y ausencia; adaptador UTF-8 exacto; límites en bytes. |
| Orden | Comparación modelo en MemTable, Bloom, SST, recuperación, scan, merge, compactación, backup y restore; prefijos y claves vacías. |
| Batch y propietario | Dos o más procesos, múltiples clientes, orden observable, atomicidad, backpressure, desconexión, caída y elección de nuevo propietario. |
| Lock y timeout | Apertura inmediata, espera, timeout, aliases, procesos duplicados, kill del propietario, endpoint obsoleto y reapertura. |
| Lectores de bloques | Dataset mayor que el presupuesto, checksum de bloque, truncamiento, corrupción tardía, índice paginado y recuperación acotada. |
| Cursor | Rangos abiertos/cerrados, límites iguales, prefijos, sobrescrituras, tombstones, cierre temprano, End, error y liberación de recursos. |
| Snapshot | Estabilidad ante put/delete/batch, flush y compactación; retención y liberación de archivos; límites de snapshots y cursores. |
| Backup/restore | Fallos durante escritura/publicación, disco lleno, permisos, archivo truncado, checksum, orden y restauración lógica exacta. |
| Migración | Fixtures reales de 0.5.0.0 / formato 0.4.0.0, preservación exacta, corrupción y fallo sin modificar fuente ni publicar destino parcial. |
| Rendimiento y recursos | Carga superior a memoria, RSS y buffers acotados, cola acotada, lecturas frías/calientes, apertura, recuperación, scans, compactación y backup. |

Las comparaciones se ejecutan con el mismo hardware, disco, toolchain, configuración, dataset y garantías de sync; se publican muestras crudas, mediana y dispersión con al menos cinco repeticiones por caso. Operaciones comparables se contrastan contra baseline fijada antes de implementar. El gate objetivo es no exceder 5% de regresión confirmada en latencia mediana o throughput, y no aumentar RSS máximo bajo configuración equivalente; diferencias dentro de variabilidad quedan inconclusas y requieren más muestras.

El release se acepta solo si todas las garantías funcionales están verificadas, la memoria de lecturas y la cola de coordinación permanecen dentro de los presupuestos configurados, no se pierden batches confirmados y cada migración/restauración exitosa reproduce exactamente su vista de origen.

## 8. Riesgos que el diseño debe resolver durante la implementación

- Diferencias de orden actuales: cualquier divergencia entre orden UTF-8 previo y bytes canónicos requiere reconstrucción, nunca reinterpretación.
- Identidad de endpoint: aliases, permisos y limpieza tras caída deben evitar dos propietarios o conexiones no autorizadas.
- Retención acumulada: cursores largos pueden impedir reclaim de SSTables; presupuestos y métricas deben hacer visible este costo.
- Solicitudes con respuesta perdida: CommitUnknown debe estar claro en ambas APIs y no inducir reintentos automáticos.
- Validación de apertura: recuperar con RAM acotada puede aumentar latencia; publicar la curva de apertura versus tamaño y nivel de validación.
- Registros grandes: el máximo debe ser finito y contabilizado en memoria, IPC, cursor y restauración.
